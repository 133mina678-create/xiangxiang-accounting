# 補充／修正帳單操作與發布

## 使用流程

- 「補記消費」新增真實漏記費用；「修正帳單」關聯原消費，只使用修改前後差額。
- 草稿不倒數、不改正式餘額、不建立付款。正式送出後才由資料庫時間開始共同 48 小時期限。
- 必要確認者由資料庫依付款人、修改前後分攤者與內容變動自動補齊，前端不能排除。
- 全員確認且無異議可提前手動結算；期限到達後仍須手動結算。逾期未回覆不會產生假的確認時間。
- 異議／拒絕只由提出者撤回；修改實質內容建立新版本，舊爭議保留至提出者明確接受新版。
- 臨時成員的帳務正常納入，但不使用不存在的登入身份建立必要待辦。

## 與主帳及付款的關係

- 獨立補記不重開主帳確認，也不重排主帳付款。
- 主帳尚未鎖定時，修正通過後只替換該筆有效消費，並只更新受影響者的主帳確認。
- 主帳已鎖定時，原快照與歷史付款不可變；修正只建立獨立差額快照。尚未付款且可能受影響的原交易會先暫停，核對通過後由守恆差額批次取代。
- 已有付款證明、爭議或完成付款時不改寫原付款；仍沿用既有轉帳證明、收款確認與 72 小時流程。

## Migration 與發布順序

1. 先套用 `202610270002_supplemental_bills.sql`。它只新增資料表／欄位／索引／RPC 與約束，不 seed、不刪除或重算歷史資料。
2. 執行 `supabase/verify.sql`；確認新 RPC 存在、RLS 啟用、匿名角色沒有資料表直接權限。
3. 再發布相同 commit 的前端。若 migration 尚未就緒，新版操作會顯示 RPC 錯誤，不會靜默繞過核對。

## 回復策略

前端可回復到上一個 Vercel deployment；新增資料表與 nullable 欄位保留，以維持向後相容。不要 drop 新表、移除後端門檻或刪除已建立的補充帳務。若新流程需暫停，應停用「新增補充費用」入口並保留既有主帳付款能力；已送出的帳單由新版修復後繼續處理。

共享秘密連結與「我是誰」仍是朋友協作身份，不是登入級身份驗證。持有秘密連結的人可切換固定成員身份；介面與 activity log 只能記錄所選身份，不能證明真實本人。
